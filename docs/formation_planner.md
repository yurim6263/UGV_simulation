# 편성 계산기: 목표 위치에 맞는 제대별 UGV 투입 대수

지휘관이 정한 목표(위치)에서 **제대마다 UGV를 몇 대 투입할지(1~3대)** 를 서버가 시뮬레이션으로 계산한다. UGV는 총 9대를 보유하고, 유인기는 목표마다 1대(제대 3개)다.
편성은 모드에 고정된 값이 아니라 목표가 바뀌면 다시 계산된다 (옛 방식은 맨 아래 "변경 이력" 참고).

코드: `backend/app/simulation/formation.py`(계산), `backend/app/services/plan_service.py`(임무 연결, 재사용), `backend/app/api/plan.py`(API),
`backend/scripts/precompute_formation.py`(기본 목표 사전 계산), 테스트 `test_formation.py`, `test_plan_api.py`.

## 방법

기상과 거리를 따로 계산하지 않는다. 엔진이 위험도 지도와 거리를 이미 반영하므로, **후보 편성을 엔진으로 돌려서 비교한다.**
후보는 제대당 1~3대의 모든 조합(제대 3개면 27가지, 투입 합계가 보유 대수를 넘는 것은 제외)이다.

### 계산량 줄이기: 제대를 하나씩 따로 시험해서 합친다
27가지를 전부 직접 돌리면 약 110초(작업자 4개)라 화면에서 쓰기 어렵다. 엔진에서 제대들은 서로 영향을 주지 않는다
(경로 분산 페널티, 운용자, 이동이 제대별이고, 공유하는 것은 난수 순서와 결과 집계뿐). 그래서:

- "제대 i가 목표 i로 UGV n대를 보낼 때"를 단독 에피소드로 돌린다 (제대 3 × n 3 × 시드 4 × 모드 3 = 108회, 약 45~55초).
- 편성 (a, b, c)의 결과는 제대별 결과를 합친다.

| 지표 | 합치는 방법 |
|---|---|
| 도착률, SOS, 개입 | 제대별 합 (도착률은 도착 합 / UGV 합) |
| 작전 시간 | 가장 늦게 끝난 제대 |
| 수색 면적 | 수색한 칸의 합집합 (겹치는 칸은 한 번만) |
| 운용자 과부하 | 과부하였던 턴의 합집합 |

제대마다 다른 난수를 쓴다 (같은 난수를 쓰면 제대 사이에 가짜 상관이 생긴다). 시드가 같으면 결과가 같아서 계산은 결정적이다.

### 검증: 합성이 직접 시뮬레이션과 맞는가
균형 모드, 기본 목표에서 6개 편성을 합성값(시드 6개)과 3제대를 직접 돌린 값(시드 8개)으로 비교했다.

| 편성 | 수색 (합성 / 직접) | 작전 시간 (합성 / 직접±표준오차) | 과부하 (합성 / 직접) |
|---|---|---|---|
| 1-1-1 | 0.402 / 0.394 | 202 / 188 ± 8 | 0 / 0 |
| 3-3-3 | 0.493 / 0.500 | 233 / 234 ± 4 | 25 / 26 |
| 1-3-2 | 0.463 / 0.463 | 227 / 235 ± 4 | 15 / 18 |
| 2-1-3 | 0.455 / 0.432 | 213 / 225 ± 8 | 7 / 6 |
| 3-1-2 | 0.442 / 0.434 | 220 / 225 ± 6 | 12 / 9 |
| 2-2-2 | 0.472 / 0.462 | 222 / 220 ± 7 | 5 / 5 |

- 수색 면적은 대부분 0.01 안팎으로 맞고(최대 0.023), 나머지도 직접 시뮬레이션의 표준오차 1~2배 안에 들었다. 가장 큰 차이는 1-1-1의 작전 시간(표준오차의 약 1.8배).
- SOS는 합성이 직접보다 평균 약 0.4~1.3건 낮게 나오는 경향이 있으나 표준오차 안이다.
- 자동 테스트(`test_composition_matches_direct_simulation_for_coverage_and_arrival`)가 작은 시나리오로 같은 확인을 한다 (수색 면적 0.04 이내).
- **한계**: 6개 편성, 한 가지 모드와 목표에서 검증했다. 다른 목표에서 합성이 틀어지는지는 확인하지 않았다 (화면에 표시되는 추천 편성은 실제 3제대 실행으로 다시 돌려서 결과를 보여 주므로, 합성 오차가 화면의 KPI에 섞이지는 않는다).

## 모드는 "무엇을 우선하나"만 정한다

모드의 전술 성향(산개, 기상 민감도, 출격 지연, 목줄 거리)은 NSGA-II 결과의 대표 전술에서 가져온 값이고 목표에 따라 바뀌지 않는다. 모드마다 이 성향으로 따로 시험한다.

| 모드 | 편성 선택 |
|---|---|
| 정밀 | 도착률 80% 이상 중 **수색 면적 최대** |
| 신속 | 도착률 80% 이상 중 **작전 시간 최소** |
| 균형 | 도착률 80% 이상 중 "수색 면적 손해 + 부담(작전 시간·운용자 과부하의 평균) 손해"가 최소 (손해 = 최선값과의 차이 / 범위) |

- 차이가 우연 수준(수색 1%p, 작전 시간 5분 이내)이면 UGV가 적은 편성을 고른다 (자산 절약).
- 도착률 80%를 만족하는 후보가 없으면 도착률이 가장 높은 후보 중에서 고르고 화면에 "제약 불충족"을 표시한다.
- **균형 규칙은 테스트가 잡은 설계 오류를 고친 것이다.** 처음에는 수색, 시간, 과부하를 같은 비중으로 합쳤는데, 시간과 과부하 둘 다 작은 편성이 유리해져 균형이 신속과 같은 편성(1-1-1)을 골랐다. 이득(수색)과 부담(시간·과부하 평균)을 같은 비중으로 보도록 바꿨다.

기본 목표에서의 결과 (보통 강도, 정찰 30분, 시드 4개):

| 모드 | 편성 | 투입 | 도착률 | 수색 | 작전 시간 | 과부하 |
|---|---|---|---|---|---|---|
| 정밀 | 3-3-1 | 7대 | 93% | 49.3% | 230분 | 15분 |
| 균형 | 2-3-2 | 7대 | 96% | 49.2% | 228분 | 10분 |
| 신속 | 2-1-1 | 4대 | 100% | 39.4% | 198분 | 0분 |

## 흐름과 재사용

1. 지휘관이 "시뮬레이션 실행" → 임무 생성 → `POST /api/missions/{id}/plan`(백그라운드 계산, `GET`으로 진행률 done/total) → 모드별 실행(계산된 편성 사용).
2. 같은 입력이면 계산을 다시 하지 않는다: 입력의 해시(`cache_key`: 출발지, 목표, 정찰 시간, 시간 한도, 날씨 강도, 시드, 모드 전술, 보유 대수, 계산기 버전)가 같은 완료된 계산(DB) →
   기본 목표 저장본(`data/formation/default_plan.json`) → 새로 계산, 순서로 찾는다.
3. 계산 결과가 없으면(직접 API 호출, 계산 실패, 계산 뒤 목표를 바꿈) 보유 대수를 제대에 고르게(제대당 최대 3대) 나눈다. 뒤에 목표가 바뀐 임무에는 옛 계산을 쓰지 않는다 (키가 달라진다).
4. 서버가 재시작되어 멈춘 계산은 FAILED로 표시한다 (진행률은 서버 메모리에만 있다).

작업자 수는 `PLAN_WORKERS`(기본 4)로 조절한다. 작업자 하나가 메모리를 약 180MB 쓴다. 병렬 실행이 실패하면 한 프로세스로 다시 시도한다 (느리지만 끝낸다).
엔진, 모드 전술, 계산기 버전이 바뀌면 `python scripts/precompute_formation.py`로 기본 목표 저장본을 다시 만든다 (키가 달라져 옛 저장본은 자동으로 쓰이지 않는다).

## 한계

- **"최적"은 시뮬레이션 추정에서 가장 좋다는 뜻이다.** 시드가 4개뿐이라 작은 차이는 우연일 수 있다 (화면의 행에 마우스를 올리면 수색·시간의 편차가 보인다).
- 제대당 1~3대로 제한한다 (4대 이상이 더 좋을 수 있으나 요구 범위 밖이다). 편성 후보만 탐색하고 제대-목표 배정(입력 순서 고정)과 전술 성향(모드 고정)은 탐색하지 않는다.
- 편성 계산에는 UGV 비용 항목이 없다. 대수를 줄이는 유일한 압력은 동률일 때 적은 쪽을 고르는 규칙과 신속 모드의 작전 시간 기준이다.
- 날씨는 한 번의 사례로 고정이고 강도만 바뀐다. 다른 날씨에서의 편성은 이 계산으로 알 수 없다.
- 합성 검증은 6개 편성, 한 모드와 목표에서만 했다.

## 변경 이력 (이전 방식, 현재는 쓰지 않음)

이전에는 모드(균형/정밀/신속)마다 3-3-3, 4-3-2, 3-4-2 같은 **고정 편성**이 서버 실행에 쓰였다. 이 값은 NSGA-II 최적화가 팀원 시나리오의 기본 목표 3곳에서 찾은 것이라
다른 목표에는 맞지 않았고(지휘관이 입력한 목표와 제대-목표 배정도 어긋났다), 그래서 위의 편성 계산기로 바꿨다. **현재 서버 실행은 NSGA-II의 편성과 배정을 쓰지 않는다.**
NSGA-II 결과는 모드의 전술 성향(산개, 기상 민감도, 출격 지연, 목줄 거리)의 근거로만 남아 있다 (`docs/optimization_report.md`).
