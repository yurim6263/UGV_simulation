# 데이터 규약 (Data Contract)

시뮬레이션과 지도가 읽는 데이터의 형식을 한 곳에 정리한다. 코드(`backend/app/simulation/algo/`)와 이 문서가 다르면 코드를 기준으로 문서를 고친다.

## 1. 작전 지역

| 항목 | 값 |
|---|---|
| 지역 | 폴란드 그단스크 인근 |
| 크기 | 약 22km × 22km, **111 × 111 셀**, 셀 크기 200m |
| 좌표 범위 | 위도 54.32~54.52, 경도 18.30~18.64 |
| 좌표계 | 위경도 EPSG:4326 (표시), EPSG:3035 (거리) |
| 행/열 방향 | row 0 = 북쪽, col 0 = 서쪽 |

격자 크기와 위경도 변환은 **하드코딩하지 않고 정적 지형 parquet에서 읽는다** (`sim_config.py`). 작전 구역 밖 좌표는 경계로 밀어 넣지 않고 `ValueError`를 낸다.

기본 데이터셋은 `map_20km`이다. 환경변수 `SIM_DATASET=map_2km`로 소규모 개발용 샘플(11×11)을 쓸 수 있다.

## 2. 정적 지형 (`data/map_20km/static/Test_sim_input_200m_bbox_20km.parquet`)

| 컬럼 | 설명 |
|---|---|
| `cell_id`, `row`, `col` | 셀 식별자와 격자 위치 (격자가 완전해야 한다: 12,321행) |
| `x_m`, `y_m` | EPSG:3035 좌표(m) |
| `lat`, `lon` | 셀 중심 위경도 |
| `lc_code` | 지표 피복 코드 (ESA WorldCover 체계로 보임) |
| `mask_good` | 위성 관측 품질이 양호한지 |
| `roads_dist_to_drivable_road_m`, `roads_has_drivable_road` | 가장 가까운 주행 가능 도로까지의 거리 / 50m 이내 도로 존재 여부 |

지형 계수는 `app/simulation/terrain.py`에서 한 번만 정의한다. **통행 불가는 수역(코드 80)뿐**이며 경로 탐색에서 해당 셀의 간선을 제거한다. (이전의 "건물 지역 50 = 통행 불가"는 잘못이었다: 팀원 UGV는 경로의 약 21%를 코드 50 셀 위에서 지났고 정찰지 POI-2도 코드 50이다.) 나머지 계수는 팀원 경로가 거의 직선이라는 관찰에 맞춰 약하게 둔 **가정값**이다.

## 3. 동적 위험도 (`data/map_20km/dynamic/`)

| 컬럼 | 의미 | 범위 |
|---|---|---|
| `normalized_c_total` | 종합 위험도 LTWR (기동 60% + 센서 40% + 보정) | 0~1 |
| `c_mob_prime` | 기동성 위험도 | 0~1 |
| `c_sen_prime` | 센서 운용 위험도 | 0~1 |

```
dynamic/actual/sim_cost_map_YYYYMMDD_HHMM.parquet                       # 실황, 10분 간격
dynamic/forecast/<모델시각 YYYYMMDD_HHMM>/sim_cost_map_<목표시각>.parquet   # 예보, 모델시각당 18개(180분)
```

- **시각 표기**: 자정 이후를 `24xx`, `25xx`로 이어 쓴다 (예: `20230630_2410` = 2023-07-01 00:10). 로더가 정규화한다. (이전에는 이 표기 때문에 실황 31개 중 19개가 조용히 버려졌다.)
- **희소성**: 동적 파일은 경로 버퍼 안의 셀(약 10,000개)만 담는다. 파일에 없는 셀은 **데이터 없음(NaN)** 이며 "위험 없음(0)"이 아니다.
- **계획/실행 분리**: 경로 계획은 실황(현재) + 예보(미래)만 본다. 예보가 없으면 직전 레이어를 이어 쓰고(persistence) 미래의 실황을 대신 쓰지 않는다. 이동 결과는 실황으로 판정한다(`Environment.actual_at`).
- 구형 2km 샘플은 `tactical_cost`/`mobility_risk`/`sensor_risk` 컬럼을 쓰며 로더가 함께 지원한다.

## 4. AP (행동력) 변환

식(`algo/ap_resolver.py`의 `resolve_tile_entry`):

```
r  = 0.6·c_mob + 0.4·c_sen           (= normalized_c_total)
AP = int((80,000 + 320,000·r²) × (대각선 이동이면 1.4, 아니면 1.0))
```

턴(10분)당 AP는 에이전트마다 1,000,000이고 매 턴 초기화된다(남은 AP는 소멸).

**검증 결과와 한계** — 팀원 이동 기록의 연속된 이동 행에 이 식을 적용해 비교했다:

| 대상 | 비교한 이동 수 | 정확히 일치 | 평균 오차 |
|---|---|---|---|
| UGV | 557 | 약 70% | 약 3.7% |
| 유인기 | 190 | 약 63% | 약 6.9k AP |

식의 형태(위험도의 제곱에 비례, 대각선 1.4배)는 맞지만, 팀원 시뮬레이터는 참조하는 시간 레이어나 보정항이 조금 다를 수 있다. 오차는 대부분 실제 AP가 식보다 2~3% 작은 방향이다.
사고 확률도 같은 기록과 대조했다 (`P_MAX_MOB=0.20`, `P_MAX_SEN=0.15`, 위험도의 제곱에 비례). 팀원의 "강수 환경" 사례에서 보고된 SOS 약 44~46회를 이 저장소의 20km 데이터(평균 위험도 0.77)에서 49~55회로 재현했다.

## 5. 시뮬레이션 이동 기록 (재생 데이터)

팀원 시뮬레이터가 만든 모드별 이동 기록(`recommended_history_enriched_{balance,explore,rush}_2.csv`)의 컬럼:

`seq_idx`, `turn_idx`, `agent_id`, `row`, `col`, `lat`, `lon`, `action`, `ap`,
`normalized_c_total`, `c_mob_prime`, `c_sen_prime`, `rain_mmph`, `swvl1`, `sde_m`, `fog_prob`, `vis_class`, `risk_grade` 등.

- `agent_id`: `UGV_<제대>_<번호>`, `Manned_<제대>`, `OP_<제대>` (제대 = Alpha/Bravo/Charlie = 1/2/3제대)
- `seq_idx`: 전 에이전트에 걸친 단조 증가 순번. `(turn_idx, seq_idx)`가 재생의 프레임 기준이다.
- `action`: `MISSION`, `HOLD_PACE`, `HOLD_EMERGENCY`, `NO_AP`, `IDLE`, `RECALL`, `SOS_SENSOR`, `SOS_MOBILITY`, `SOS_WAIT`, `BLIND`, `INTERVENE->UGV_x_n`, `ARRIVED`, `TEAM_DONE`, `NO_PATH`
- `ARRIVED`/`TEAM_DONE`은 유인기에만 기록된다. **UGV의 도착은 "마지막 위치가 정찰지(POI) 셀인가"로 판정한다.**
- 정찰지 좌표 (lat, lon) → 셀: POI-1 (54.40, 18.54) → (57, 83), POI-2 (54.33, 18.36) → (103, 29), POI-3 (54.37, 18.50) → (76, 72). 출발지 (54.48, 18.32) → (22, 7).

화면은 서버가 계산한 기록을 `GET /api/runs/{id}/replay`로 받아 재생한다. 예전에 있던 정적 JSON 변환 스크립트와 저장본(팀원 기록, 엔진 실행)은 제거했다.

- `scenario.team_modes`: 제대별 지정 모드(`balance|explore|rush`). 통제관에게는 담당 제대 것만 온다.
- 지휘관은 `GET /api/missions/{id}/assigned-replay`로 제대마다 지정한 모드의 기록을 합친 같은 형식의 데이터(`mode.mode = "assigned"`)를 받는다. 합칠 때 제대마다 `seq_idx`를 30000씩 띄운다 (화면이 `턴 x 100000 + seq`로 프레임을 매기므로 기록 순번 + 60000 < 100000 이어야 한다).
- `GET /api/runs/{id}/replay`와 `run_id`가 경로에 있는 API는 통제관이 담당 제대에 지정된 모드의 run만 읽을 수 있다.

## 6. 알려진 불일치 (확인 필요)

- **날짜 라벨**: 시뮬레이션 노트북 시작 시각은 2024-07-03 04:00, 사례 폴더명은 `20230726`, 저장소의 20km 실황은 2023-06-30으로 서로 다르다. 화면에는 절대 날짜를 표시하지 않고 `T+분`만 쓴다.
- **LTWR 용어**: 문서마다 풀이가 다르다 (결과보고서 "지상작전기상위험도 Land Tactical Weather Risk", 노션 "Readiness", ERD 문서 "Limited Technical Weather Requirements", 코드 주석 "Land-Terrain-Weather-Road"). 결과보고서 표기를 기준으로 통일한다.
- **지형 코드 범례**: `map20km_loader.LC_COLORS_RGBA`의 라벨(40=도시, 50=수역, 60=도로)은 ESA WorldCover(40=농지, 50=건물, 60=나지, 80=수역, 90=습지)와 다르다.
- **통신 마스크 이름**: `mask_18km`는 반경 9셀 = 실제 **1.8km**이다 (이름의 숫자는 0.1km 단위).

## 7. 시뮬레이션 엔진 (`algo/episode.py`)

`run_episode(env, spec, genes, seed) → EpisodeResult(log, metrics)` — DB/서버와 무관한 순수 코어.

- **구조**: 3개 제대(Alpha/Bravo/Charlie) × [유인기 + 운용자(OP) + UGV 2~4]. 1턴 = 10분.
- **시간 의존 경로 탐색** (`algo/planner.py`): 시간을 AP 누적량으로 센다. 도착 시점의 날씨 레이어를 참조하는 비용으로 격자 전체에 Dijkstra를 돌리고, 도착 시점 추정이 안정될 때까지 반복한다. (이전 PathFinder3D는 "1칸 = 시간 1단계"라 18개 레이어로 17칸까지만 계획할 수 있어 20km 지도에서는 경로가 나오지 않았다.)
- **계획/실행 분리**: 계획은 실황+예보, 사고와 AP 소모는 실황으로 판정한다. 예보가 없으면 직전 레이어를 이어 쓴다.
- **사고**: 칸에 들어가는 순간 1회 판정(지연 평가). 사고가 나면 그 자리에서 SOS → 대기열 → 운용자 개입(다음 턴 복귀).
- **목줄**: 유인기와의 거리가 `hold_km`(1.5)를 넘으면 대기(`HOLD_PACE`), `recall_km`(1.8) 이상이면 복귀(`RECALL`), `resume_km`(1.2) 이내가 되면 재개. 유인기는 가장 먼 UGV가 `follow_gap`(5셀=1km) 이내가 되도록 따라가며, 제대에 SOS가 있으면 정지(`HOLD_EMERGENCY`).
- **유전자(Genes)**: 출격 지연, 산개 가중치, 기상 민감도, 목줄 임계값(대기/복귀/재개). 서버의 모드 프리셋(`presets.py`)의 **유전자**는 `data/optimization/pareto.json`(NSGA-II 결과)의 신속/정밀/균형 원형이며, 파일이 없으면 팀원 기준 프리셋을 쓴다. **편성(제대별 UGV 수)과 제대-목표 배정은 프리셋을 쓰지 않는다.** 편성은 편성 계산기가 목표 위치에서 계산하고(`docs/formation_planner.md`), 배정은 입력 순서(목표 i → i제대)다. 결과는 `docs/optimization_report.md` 참고.
- **시나리오 강도** `weather_scale`: 데이터의 위험도에 곱하는 배율. Clear 0.15 / Moderate 0.3 / Severe 1.0.
  **이 저장소의 20km 데이터는 전체가 악조건**(평균 위험도 0.77 → 0.61)이라 Severe(1.0)에서는 어떤 편성도 도착하지 못한다. 서버 기본값은 Moderate(`SIM_WEATHER_SCALE`).
- **지표**: V1 수색 면적 비율(최대화), V2 작전 시간(최소화), V3 운용자 과부하 시간(최소화) + SOS, 개입, 평균 대기, 운용자 가동률, 도착률. 기록의 컬럼은 팀원 CSV와 같아 재생 화면이 그대로 읽는다.
- **정찰(체류) 시간**: 목표의 `patrol_duration_sec`를 올림한 턴 수만큼 도착 후 정찰지에 머문 뒤 임무가 끝난다(`PATROL` 행동). 서버 실행에서는 UGV 도착 시 `run_patrol_events`가 기록되어 대시보드의 정찰 카운트다운이 쓴다.
- **재생형 스트리밍**: 서버는 에피소드를 먼저 끝까지 계산(선택한 모드와 기준선 2회, 약 10초)한 뒤 턴마다 DB/WebSocket으로 흘려보낸다. "실시간"처럼 보이지만 미리 계산된 결과의 재생이다. 실행 중 취소는 턴마다 확인한다.

### 개요(노션 설계/결과보고서)와 다른 점 — 의도적이거나 아직 못 한 것

| 설계 | 현재 구현 | 상태 |
|---|---|---|
| NSGA-II로 유전자 5종 탐색 | 편성·목표 배정 + 유전자(산개, 기상 민감도, 출격 지연, 목줄) 탐색 구현. 모드 프리셋의 **유전자**를 결과로 교체 (편성·배정은 기본 목표 전용이라 서버 실행에는 쓰지 않고 편성 계산기가 대신한다) | 완료 (4단계) |
| Gene 5 기동 속도(Adaptive Speed) | 없음 | 4단계 |
| 소프트 지오펜싱(회랑 밖 +4.0) | 동적 데이터가 있는 회랑(NaN 아닌 셀) 밖은 아예 진입 불가(하드 제한) | 미정 |
| 도로 선호(도로 컬럼) | 도로 정보는 읽지만 비용에 쓰지 않음 | 미정 |
| 날씨 예측(ConvLSTM/XGBoost) | 저장소의 예보 parquet을 그대로 사용 | 6단계 |
| 몬테카를로 신뢰구간 | 새 시드 30회의 평균 ± 95% 신뢰구간, 하위 5% (표본이 작아 구간이 넓음) | 완료 (4단계) |
| 센서 시야 반경이 기상에 따라 변함 | V1 계산에만 반영(`1 - 센서 위험도`) | — |

- **한계**: 날씨 외 변수(강수·토양수분 등)는 기록하지 않는다. 에피소드 1회는 3~7초(24턴, 9 UGV)이며 시간의 대부분은 경로 재계획이다. 최적화/몬테카를로는 `app/simulation/batch.py`로 프로세스를 나눠 돌린다 (12코어에서 약 1.4초/에피소드, 환경 적재 포함). 지형 계수와 개입 AP 식은 가정값이다. `GET /api/runs/{id}/replay`는 지휘관이면 어떤 run이든, 통제관이면 자기 제대의 지정된 모드 run만 읽을 수 있다. 다른 임무의 run 인지는 검사하지 않는다(run 소유자 검사 없음).

### 경로 탐색 속도 (3단계)

계획 1회 약 80ms → 15ms(5배). 에피소드 24턴 23초 → 3~7초. 결과(경로, AP)는 이전 구현과 72개 무작위 경로에서 완전히 같다.
- 간선 구조(CSR indptr/indices)를 한 번만 만들고 반복마다 비용 배열만 바꾼다 (매번 정렬하며 새로 만들던 비용 제거).
- 도착 시점 AP 누적을 파이썬 루프 대신 예측 트리 위의 포인터 점프로 계산하고, 경로에 영향을 주는 노드(목표보다 가까운 노드)만 갱신한다.
- 반복의 수렴 조건을 같은 영역으로 한정했다.
